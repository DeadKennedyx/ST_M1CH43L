Following an evolving XOR key in GDB

10.09.26 / first iteration

The part I remembered from a Hack The Box forensics challenge was the XOR. The annoying part was that the state kept changing. Finding one key value didn't explain the rest of the buffer.

I wanted to work through that idea again, slowly enough to understand what each instruction was doing. So this uses a separate practice binary, xor95, built for the exercise. It isn't a reconstruction of the HTB challenge. It has a 95-byte buffer, two evolving state bytes, and a synthetic flag. The program changes its data in memory; it doesn't execute the decoded buffer.

This draft stops after the first iteration. There are already a few things worth getting straight before letting the other 94 run.

The first XOR wasn't decoding anything

The practice executable is a stripped Linux x86-64 ELF, compiled without optimization and with fixed executable addresses to make this first session easier to follow. The addresses below belong to this build. A rebuild can change them, and stack or loader addresses can differ between sessions.

cd ~/xor95-lab
readelf -h xor95
strings -a -n 6 xor95
gdb -q ./xor95

strings shows printable sequences in the file. The flag doesn't appear. That alone proves very little: unreadable bytes could be compressed data, integers, or any number of other things.

(gdb) set pagination off
(gdb) set disassembly-flavor intel
(gdb) starti
Program stopped.
0x00007ffff7fe3d40 in ?? () from /lib64/ld-linux-x86-64.so.2
(gdb) x/20i $pc
(gdb) info files

starti stops at the first instruction of execution, which in this session is inside the dynamic loader. The loader prepares the program and its libraries. We're not in the program's own startup code yet. $pc is GDB's name for the program counter, and x/20i $pc disassembles 20 instructions starting there.

One of the loader instructions is xor ebp,ebp. Easy to spot. Also easy to misinterpret: XORing a value with itself produces zero. This instruction clears a register. Seeing the word xor doesn't establish that a payload is being decoded.

info files gives the executable entry point as 0x401050. We can stop there directly:

(gdb) tbreak *0x401050
(gdb) continue
(gdb) x/20i $pc

tbreak sets a temporary breakpoint that disappears after it's hit. The * tells GDB to interpret this as an instruction address. The useful part of the resulting startup disassembly is:

0x40105f: xor  r8d,r8d
0x401062: xor  ecx,ecx
0x401064: mov  rdi,0x4011a2
0x40106b: call QWORD PTR [rip+0x2f67]  # 0x403fd8

More register clearing, followed by an address passed to a runtime call. In this C startup sequence, the first argument to the C runtime startup function is the address of main. That makes 0x4011a2 our candidate.

(gdb) tbreak *0x4011a2
(gdb) continue
(gdb) x/30i $pc

0x4011a2: push rbp
0x4011a3: mov  rbp,rsp
0x4011a6: sub  rsp,0x10
0x4011aa: mov  esi,0x5f
0x4011af: mov  edi,0x404040
0x4011b4: call 0x401136

The rest of this function calls write, read, and write again before returning. The earlier call to 0x401136 is the one to inspect. Also, x/30i just decodes 30 instructions from memory. It can keep going past a function's return into padding or another function; the amount requested doesn't define a function boundary.

Why those registers count as arguments

This was one of my first questions: do two mov instructions followed by call always mean a function takes two parameters?

No. The CPU's call instruction saves a return address and transfers execution. It doesn't count parameters. The caller and the receiving function agree where to put them through a calling convention.

For ordinary integer and pointer arguments, the System V AMD64 calling convention used here assigns the first six register arguments in this order:

Argument:   1    2    3    4    5   6
Register:  RDI  RSI  RDX  RCX  R8  R9

So mov esi,0x5f prepares the second argument, 95 decimal, and mov edi,0x404040 prepares the first. Preparing argument two first doesn't change its position. The register determines the slot.

edi and rdi aren't independent registers. edi names the lower 32 bits of the 64-bit rdi. An x86-64 write to a 32-bit register also clears the upper 32 bits of its corresponding 64-bit register. The same applies to esi/rsi and edx/rdx.

mov esi,0x5f     ; RSI becomes 0x000000000000005f
mov edi,0x404040 ; RDI becomes 0x0000000000404040

Smaller writes behave differently. Writing al, the lowest byte of rax, leaves the other bits of rax alone.

A large program doesn't have a separate rdi for every function. Within a thread, functions reuse the same registers. We follow the instructions that last assigned their values along the actual execution path. Here, nothing overwrites the argument registers between their setup and the called function saving them. Other threads have their own register state.

We still need to check how the receiving function uses these values. There could be additional arguments prepared earlier, or the code could use a different convention. Two nearby assignments are evidence, not a function signature.

(gdb) tbreak *0x401136
(gdb) continue
(gdb) disassemble 0x401136,0x4011a2

0x401136: push rbp
0x401137: mov  rbp,rsp
0x40113a: mov  QWORD PTR [rbp-0x18],rdi
0x40113e: mov  DWORD PTR [rbp-0x1c],esi

The function saves the incoming address and length into stack memory. QWORD means eight bytes, DWORD four. After setting up rbp as a frame pointer, the code uses fixed offsets from it to locate these saved values.

(gdb) si 4
0x0000000000401141 in ?? ()
(gdb) x/gx $rbp-0x18
0x7fffffffde58: 0x0000000000404040
(gdb) x/wx $rbp-0x1c
0x7fffffffde54: 0x0000005f

si abbreviates stepi, which executes one machine instruction. si 4 requests four steps; a breakpoint or signal can interrupt that count. Here, it executes exactly the four instructions above. GDB's instruction stepping commands also include ni, which runs a call until it returns instead of stepping into the function.

An address isn't the byte stored there

The left side of that first memory read, 0x7fffffffde58, is the stack address holding our pointer. The stored value, 0x404040, points somewhere else. Keeping those two separate cleared up quite a bit for me.

Earlier, info files placed .data between 0x404020 and 0x40409f. Our pointer falls inside that initialized, writable data section. It's a virtual address in the running process, not an offset you can use directly to seek through the binary file.

The next three instructions initialize two bytes and a four-byte counter:

0x401141: mov BYTE PTR [rbp-0x1],0xa7
0x401145: mov BYTE PTR [rbp-0x2],0x3d
0x401149: mov DWORD PTR [rbp-0x8],0x0

The constants come straight from these instructions. There's no special meaning built into rbp-0x1; the program writes 0xa7 into memory at that address.

(gdb) si 3
(gdb) x/bx $rbp-0x1
0x7fffffffde6f: 0xa7
(gdb) x/bx $rbp-0x2
0x7fffffffde6e: 0x3d
(gdb) x/wd $rbp-0x8
0x7fffffffde68: 0
(gdb) x/16bx 0x404040
0x404040: 0xd7 0x76 0x95 0x4c 0xa2 0x66 0x7d 0x99
0x404048: 0xe8 0x57 0x2c 0x60 0x94 0x2c 0xb8 0xaf

In GDB's memory examination syntax, x/16bx asks for 16 bytes in hexadecimal. x/wd reads one four-byte value in decimal. The addresses printed on the left label each row; they aren't extra bytes in the buffer.

Now the loop reads one byte:

0x401152: mov   edx,DWORD PTR [rbp-0x8]
0x401155: mov   rax,QWORD PTR [rbp-0x18]
0x401159: add   rax,rdx
0x40115c: movzx eax,BYTE PTR [rax]
0x40115f: mov   BYTE PTR [rbp-0x9],al

rdx holds the index here because the first instruction loads it from the counter. It isn't permanently an index register. The second instruction loads the buffer address into rax. Then add rax,rdx adds the two numbers:

buffer start + index = address of selected byte

0x404040 + 0 = 0x404040
0x404040 + 1 = 0x404041
0x404040 + 2 = 0x404042

That's the address calculation behind buffer[index]. Each element is one byte, so adding the index is enough. A four-byte element would need an offset of index * 4.

The addition only calculates where to read. movzx eax,BYTE PTR [rax] actually reads the byte at that address and zero-extends it into eax. This overwrites the old address in rax. The register has a new job now. The last instruction saves the byte in another stack location, [rbp-0x9], before anything changes it.

Following the byte through XOR

This is the evidence that was missing from the first xor ebp,ebp. We have a byte loaded from the buffer, two XORs with separate state values, and a store back into the buffer:

0x401162: movzx eax,BYTE PTR [rbp-0x9]
0x401166: xor   al,BYTE PTR [rbp-0x1]
0x401169: mov   ecx,DWORD PTR [rbp-0x8]
0x40116c: mov   rdx,QWORD PTR [rbp-0x18]
0x401170: add   rdx,rcx
0x401173: xor   al,BYTE PTR [rbp-0x2]
0x401176: mov   BYTE PTR [rdx],al

The middle three instructions calculate the destination address again, this time in rdx. That register held the index earlier. Already reused.

We can describe the operation in C-like notation:

buffer[index] = original_byte ^ state_a ^ state_b;

At this stage the assembly establishes an XOR transformation. Decoding is our interpretation to test by inspecting its output. One printable character is a start; a coherent message would be stronger evidence.

(gdb) tbreak *0x401166
(gdb) continue
(gdb) p/x $al
$1 = 0xd7
(gdb) si
(gdb) p/x $al
$2 = 0x70

That first step computes 0xd7 XOR 0xa7 = 0x70. The result goes into al, the destination operand. The state byte at [rbp-0x1] stays unchanged.

(gdb) si 3
(gdb) x/i $pc
=> 0x401173: xor al,BYTE PTR [rbp-0x2]
(gdb) si
(gdb) p/x $al
$3 = 0x4d
(gdb) si
(gdb) x/4bx 0x404040
0x404040: 0x4d 0x76 0x95 0x4c

The second XOR gives 0x70 XOR 0x3d = 0x4d, ASCII M. The final step writes it into memory. Only the first byte has changed. GDB's numbered value labels, such as $3, depend on how many print commands you've already run.

The state moves on

Now the part I wanted to revisit. The first state byte gets a fixed increment:

0x401178: add BYTE PTR [rbp-0x1],0x17

(gdb) si
(gdb) x/bx $rbp-0x1
0x7fffffffde6f: 0xbe

0xa7 + 0x17 = 0xbe. Because the destination is one byte, an eventual overflow wraps modulo 256.

The other update takes more instructions:

0x40117c: movzx eax,BYTE PTR [rbp-0x2]
0x401180: lea   edx,[rax+rax*1]
0x401183: movzx eax,BYTE PTR [rbp-0x2]
0x401187: shr   al,0x7
0x40118a: or    eax,edx
0x40118c: xor   al,BYTE PTR [rbp-0x9]
0x40118f: mov   BYTE PTR [rbp-0x2],al

lea is the exception to the tempting idea that brackets always mean a memory read. Here it calculates rax + rax * 1 and stores the result in edx. It doubles the number. No memory is read by this instruction.

I had to pause here because doubling a number and shifting bits sounded like different operations. In binary, moving every bit one position left doubles its value:

0x3d = 00111101 = 61
0x7a = 01111010 = 122

That supplies the left-shift portion of a rotation. The code reloads the original byte and shifts it right seven places to extract its highest bit. or eax,edx combines the two pieces. Taking the low byte of that result gives an eight-bit rotation left by one.

With 0x3d, the highest bit is zero, so doubling and rotating happen to give the same value, 0x7a. To see the difference, consider 0xad as a separate arithmetic example:

Original:              10101101  0xad
Shift left, low byte:  01011010  0x5a
Wrap highest bit:      01011011  0x5b

Doubling gives 0x15a; keeping the low byte gives 0x5a. Rotation also brings the original highest bit around to the bottom, producing 0x5b.

Back in our first iteration, the rotated value 0x7a is XORed with [rbp-0x9]. That's the saved original byte, 0xd7, not the decoded M. Now we know why the code kept that copy.

Next state B = 0x7a XOR 0xd7 = 0xad

(gdb) si 6
(gdb) p/x $al
$4 = 0xad
(gdb) x/i $pc
=> 0x40118f: mov BYTE PTR [rbp-0x2],al
(gdb) si 2
0x0000000000401196 in ?? ()
(gdb) x/bx $rbp-0x1
0x7fffffffde6f: 0xbe
(gdb) x/bx $rbp-0x2
0x7fffffffde6e: 0xad
(gdb) x/wd $rbp-0x8
0x7fffffffde68: 1

The six steps reach the final store. The next two execute that store and increment the index. We're now before the loop condition:

0x401196: mov eax,DWORD PTR [rbp-0x8]
0x401199: cmp eax,DWORD PTR [rbp-0x1c]
0x40119c: jb  0x401152

This is where the saved second argument returns: compare the index with 95 and branch back while it's below the length, using an unsigned comparison. The loop processes byte positions, not lines of a binary.

I'll call the first state byte the key and the second the IV-like state. Those names describe their roles in this toy construction; the assembly doesn't carry the source variable names, and this isn't a standard cipher. We can now reconstruct the update order:

original = buffer[index];
buffer[index] = original ^ key ^ iv;
key = (key + 0x17) & 0xff;
iv = rotate_left_8(iv, 1) ^ original;
index++;

XOR reverses itself if we use the same state. For the first byte, 0x4d XOR 0xa7 XOR 0x3d encodes to 0xd7, and XORing 0xd7 with those same values gets 0x4d back. But the state update needs the encoded byte in both directions. An encoder uses its output for that update; this decoder saves its input. Running this exact decoder twice wouldn't generally restore the original buffer.

That's where this session stops: instruction 0x401196, index 1, key 0xbe, IV-like state 0xad. The buffer starts with M, followed by the still-encoded byte 0x76. Next session starts there.
