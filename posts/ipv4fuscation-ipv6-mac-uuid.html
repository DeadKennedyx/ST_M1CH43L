IPv4fuscation and its IPv6, MAC, and UUID variants

31.08.26 / 9 min read

IPv4fuscation changes how bytes look. It does not encrypt them. You take four bytes, write their decimal values as one IPv4 address, and parse that address when you need the original bytes. The same process works with IPv6 addresses, MAC addresses, and UUIDs because each format represents a fixed number of bytes as text.

This experiment uses Hello, world! so you can follow every value. The input stays harmless and readable. The goal is to understand the representation, the padding, the reverse conversion, and the limits of the technique.

Start with what an IPv4 address stores

IPv4 uses a 32 bit address. That gives you four octets, and each octet holds one byte from 0 through 255. Dotted decimal notation prints those bytes as four decimal numbers separated by periods.

binary bytes:  C0 A8 01 0A
decimal text: 192.168.1.10

The text looks like a network address, but the encoder does not send a packet or assign the address to an interface. It only uses the address grammar as a text container for four bytes.

Windows exposes both directions through its IP string functions. RtlIpv4AddressToStringA formats four binary bytes. RtlIpv4StringToAddressA parses the text and writes four bytes in network order, from left to right.

Turn the message into four byte blocks

The message contains 13 bytes and no null terminator:

48 65 6C 6C 6F 2C 20 77 6F 72 6C 64 21
 H  e  l  l  o  ,     w  o  r  l  d  !

Thirteen does not divide evenly by four. The formatter always reads four bytes, so you need a complete final block. PKCS#7 padding solves that problem and also tells the decoder how many bytes to remove.

padding length = 4 − (13 mod 4)
padding length = 3

PKCS#7 writes the padding length into every padding byte. The padded buffer contains 16 bytes:

48 65 6C 6C  6F 2C 20 77  6F 72 6C 64  21 03 03 03

If your input already fits the block size, PKCS#7 adds a complete block. A four byte aligned IPv4 input receives four bytes with the value 04. That rule keeps removal unambiguous.

Format each block

The encoder reads four bytes at a time and converts each byte from hexadecimal to unsigned decimal:

Input bytes Meaning IPv4 text
48 65 6C 6C Hell 72.101.108.108
6F 2C 20 77 o, w 111.44.32.119
6F 72 6C 64 orld 111.114.108.100
21 03 03 03 ! plus padding 33.3.3.3

The program prints those strings as a C array:

const CHAR* ipv4Array[4] = {
    "72.101.108.108",
    "111.44.32.119",
    "111.114.108.100",
    "33.3.3.3"
};

Parse the addresses and remove the padding

The decoder allocates four bytes for every array element. It passes each string to RtlIpv4StringToAddressA in strict mode, writes the resulting bytes at the next four byte offset, and checks that the parser consumed the complete string.

four strings × four bytes = 16 decoded bytes

The decoder then reads the last byte. Its value is 03, so the decoder verifies that the last three bytes all contain 03. It reports 13 meaningful bytes and ignores the verified padding.

16 decoded bytes − 3 padding bytes = 13 message bytes

The function transfers the allocated buffer to its caller. The caller prints exactly 13 bytes with fwrite, then releases the allocation with LocalFree. It uses fwrite because the decoded buffer has a length but no null terminator.

The same process works at other widths

Each variant follows the same sequence. You pad the input to the format width, split it into equal blocks, format every block, parse every string, concatenate the bytes, verify the final padding, and remove it.

Representation Bytes per string Text shape Padding range
IPv4 4 Four decimal octets 1 through 4
IPv6 16 Eight hexadecimal groups 1 through 16
MAC 6 Six hexadecimal octets 1 through 6
UUID 16 Hexadecimal groups in 8, 4, 4, 4, 12 form 1 through 16

IPv6fuscation uses 16 bytes per address

IPv6 expands the address width from 32 bits to 128 bits. Its normal text form uses eight groups of 16 bit hexadecimal values. One IPv6 string therefore carries 16 input bytes.

Our 13 byte message needs three padding bytes under a 16 byte block size. The same padded data fits into one IPv6 address:

4865:6c6c:6f2c:2077:6f72:6c64:2103:303

IPv6 permits shorter spellings. A formatter removes leading zeros from a group and replaces one run of zero groups with ::. That changes the string, not the 16 decoded bytes. Your decoder should accept valid IPv6 forms and verify that the parser consumed the entire input.

On Windows, RtlIpv6AddressToStringA performs the forward conversion and RtlIpv6StringToAddressA performs the reverse conversion. The reverse function writes the bytes in network order.

MACfuscation uses six bytes per address

A common MAC address uses an IEEE EUI 48 value. It contains six bytes and usually appears as six hexadecimal pairs separated by colons or hyphens.

Thirteen bytes require five padding bytes when the block size is six. The result contains 18 bytes and produces three MAC shaped strings:

48-65-6C-6C-6F-2C
20-77-6F-72-6C-64
21-05-05-05-05-05

Windows exposes RtlEthernetAddressToStringA and RtlEthernetStringToAddressA for this representation. The process still needs full input validation, padding verification, and correct memory ownership.

These strings only look like MAC addresses. Arbitrary input controls the individual or group bit and the universal or local bit in the first octet. The resulting value does not claim an IEEE assignment and does not identify real hardware.

UUIDfuscation uses another 16 byte container

A UUID contains 128 bits, so it carries the same number of bytes as IPv6. Its common text representation uses five hexadecimal groups with lengths of 8, 4, 4, 4, and 12 characters.

In RFC byte order, the padded message has this UUID shaped representation:

48656c6c-6f2c-2077-6f72-6c6421030303

Windows provides UuidToStringA and UuidFromStringA through the RPC runtime. UuidToStringA allocates its output string, and you must release that string with RpcStringFreeA.

UUID byte order needs extra attention. RFC 9562 stores fields in network byte order, but Microsoft COM GUIDs use little endian storage for the first fields. If you copy arbitrary bytes directly into a Windows UUID structure, the first text groups can appear reordered. Use the same formatter and parser for both directions, then test the exact byte round trip.

Arbitrary bytes also control the UUID version and variant fields. The text has UUID syntax, but it does not automatically represent a standards compliant UUID version. Treat it as a UUID shaped byte container.

What changes and what stays the same

The container width changes. The padding calculation, loop stride, string buffer size, formatter, and parser change with it. IPv4 uses decimal bytes. IPv6 uses hexadecimal 16 bit groups. MAC uses hexadecimal bytes. UUID uses a fixed hexadecimal field layout.

The core data never changes. Each technique preserves the padded byte sequence and gives it a familiar text form. Deobfuscation reverses that form and removes the padding.

bytes → pad → split → format → strings
strings → parse → join → verify padding → bytes

What these techniques do not provide

These formats do not provide confidentiality, integrity, or authenticity. Anyone who recognizes the pattern can parse the strings. A debugger also sees the original bytes after the program reconstructs them in memory.

The representation still leaves clues. An array of address strings has a regular shape. The executable can reference address parsing APIs. The decode loop writes fixed width blocks into one buffer. A detector can normalize the strings and inspect the recovered bytes.

Use these techniques to study representation and analysis, not to protect secrets. If you need secrecy, use authenticated encryption and manage the key correctly.
