Reversing a private client without naming it

15.09.26 / first notes

I’m deliberately leaving the name out of this one. The application is a privately installed Windows multiplayer client, and the point of these notes is the method, not handing the internet a neat set of search terms for somebody else’s software.

The first useful thing was simply identifying what kind of Unity build I was looking at. The main executable was accompanied by a large native assembly, a metadata file, and an il2cpp_data directory. That combination is the tell: this is an IL2CPP build, so the managed code isn’t sitting around as ordinary readable assemblies waiting for ILSpy.

There were still managed-looking DLL names in the scripting assembly manifest. That was a nice little trap. They’re useful clues about namespaces and features, but they aren’t the original source. The interesting logic lives in the native binary, with type and method metadata split across the binary and the metadata file.

Metadata first, guessing later

I used an IL2CPP metadata dumper against the native assembly and the global metadata file. The generated dummy assemblies and dump.cs were enough to turn a 100-plus-megabyte wall of machine code into something searchable.

Il2CppDumper.exe \
  "path\to\GameAssembly.dll" \
  "path\to\global-metadata.dat"

The output is not a magic decompilation. A generated method such as SetEntityPermissionsRequest tells us that a type and its signature existed. It does not tell us that the client will accept arbitrary values, or that the server will honor them. That distinction matters, especially in multiplayer software where the server is supposed to make the final decision.

I renamed the application-specific identifiers in these notes. For example, one scoped-permission request becomes SetEntityPermissionsRequest here. Same meaning, less fingerprinting.

The first real lead was permissions, not a cheat switch

The generated protocol definitions contained a cluster of fields that looked much more interesting than the usual UI and analytics debris:

EntityPermissions
ResourcePermissions
EventPermissions
SuspendPermissions
TaskPermissions
AutomaticSuspendPermissions
PermissionDetails

There were also request/response pairs for changing scoped permissions, manager-level permission updates, and a broadcast-style message carrying permission state. That gives us a real flow to follow: a panel creates a request, a transport sends it, and a response or broadcast updates the UI.

Several error values explicitly represented “no permission” or a permission failure. That’s useful because it tells us the authorization boundary is expected to be enforced somewhere. It also means a local toggle may only change what the client displays while the server continues to reject the operation. A button appearing is not the same thing as authority.

Debug panels are worth checking, carefully

String extraction found names resembling a server-switching panel, a test-data selection panel, a protobuf test panel, a performance debug menu, an administration popup, and a few export tools. I’m treating these as leads, not vulnerabilities. Debug code often ships accidentally, but it can also be dead UI, development-only scaffolding, or a panel protected by a server-side role check.

The next searches are deliberately boring:

rg -n -i -C 8 \
  'SetEntityPermissionsRequest|PermissionDetails|AdminAuthorityPanel|DebugServerPanel' \
  dump.cs

rg -n -i -C 8 \
  'EntityPermissions *=|PermissionDetails *=|CanManage|IsAdmin|IsGM' \
  dump.cs

I’m looking for the enclosing class and the code that decides visibility, not just names that contain “admin.” The useful questions are: what opens the panel, what fields are populated, where is the request sent, and does the client make a local decision based on a role or permission bit?

A role-setting path, confirmed

The search produced something more concrete than a suspiciously named panel. There is a request/response pair for changing an account’s role within a managed scope:

SetScopeRoleRequest
  ScopeId
  UserId
  Role
  PermissionDetails

SetScopeRoleResponse
  Code
  ScopeId
  Role
  UserId
  PermissionDetails

The response code enum is particularly useful evidence. It includes a success value, an administrator-assignment failure, and a manager-without-authority failure. Those names don’t prove the server is secure, but they do show that the intended design includes an authorization decision after the request is sent.

SUCCESS                         = 0
ERROR_CANNOT_SET_ADMIN         = -3
ERROR_MANAGER_NO_AUTHORITY     = -6

The UI side lines up with it. An anonymized panel contains two permission toggles, a confirmation button, and an OnConfirmButtonClick handler whose generated metadata references the scoped-permission request. So the rough path is:

flowchart LR
    A[Managed-scope panel] --> B[Permission toggles]
    B --> C[Confirm handler]
    C --> D[Build role or permission request]
    D --> E[Protocol transport]
    E --> F[Server authorization]
    F --> G[Success response]
    F --> H[Permission error]
    G --> I[Update client state]
    H --> J[Show failure or leave state unchanged]

This is the point where I need to stop calling it “god mode.” The client clearly knows how to request role and permission changes. It does not follow that an ordinary account can submit an administrator role and receive it. In fact, the explicit ERROR_CANNOT_SET_ADMIN and ERROR_MANAGER_NO_AUTHORITY values suggest the opposite.

The native implementation is still unresolved because the IL2CPP dump gives method signatures and RVAs, not readable bodies. The next experiment is to inspect the native code behind the confirmation handler and the protocol registration, then record the actual role values and send path. Until that is done, the finding is “administrative protocol exposed in the client,” not “privilege escalation demonstrated.”

Working address map

Before opening Ghidra, I wrote down the metadata-to-native mapping. This avoids the easiest mistake in IL2CPP work: finding a plausible function at a nearby address and silently assigning it the wrong managed name.

Generated metadata                         Native VA
-------------------------------------------------------------
Scoped panel confirmation handler          0x18317F310
Generated confirmation callback            0x18317F680
Panel close handler                        0x18317F2B0
Resolved virtual Dispose target            0x182528A90

The first address I inspected, 0x18317F2B0, came from the generated dump entry for the panel close method. It was initially mislabeled in my notes as the confirmation handler. The correction matters because the function’s behavior is only meaningful after the managed identity is established.

0x18317F310  confirmation handler
       |
       +--> 0x18317F680  generated callback
       |
       +--> [request construction / transport]  (not resolved yet)

0x18317F2B0  close handler
       |
       +--> vtable slot 4 at object + 0x178
                    |
                    +--> 0x182528A90  BaseBehaviour.Dispose
                              |
                              +--> DisposableBehaviour.Dispose

Correction: the first virtual call was just cleanup

This was a useful wrong turn. The address was real, but its managed identity was wrong in my working notes. The generated metadata maps 0x18317F2B0 to the panel’s close handler, not the confirmation handler. Once that mapping was corrected, the decompiled behavior made much more sense.

The tail call resolves through an IL2CPP virtual table:

MOV  R9, [object]        ; class/vtable pointer
XOR  R8D, R8D           ; immediate = false
MOV  DL, 1              ; destroy now = true
MOV  RAX, [R9 + 0x178]  ; virtual method pointer
MOV  R9,  [R9 + 0x180]  ; MethodInfo*
JMP  RAX

In this metadata layout, the vtable begins at 0x138, and each virtual entry occupies 0x10 bytes: an 8-byte function pointer followed by an 8-byte method-information pointer. Therefore:

(0x178 - 0x138) / 0x10 = 4

That makes +0x178 virtual slot 4 and +0x180 its paired MethodInfo*. Following the inheritance chain in the generated metadata led to the slot-4 override:

ScopedManagementPanel
  -> PrefabObject
    -> BaseBehaviour
      -> DisposableBehaviour

BaseBehaviour.Dispose(bool destroyNow = true, bool immediate = false)

The resolved target was renamed BaseBehaviour_Dispose in Ghidra. The call is therefore equivalent to:

this.Dispose(true, false);

The values 1 and 0 are disposal controls, not permission bits. The real confirmation path remains the method at 0x18317F310, with its generated callback at 0x18317F680. This is exactly why the metadata mapping has to be checked before interpreting constants in a native function. A plausible-looking integer is not evidence by itself.

What the strings did not show

No plaintext administrator password, session token, or obvious god-mode boolean appeared in the collected strings. The apparent URLs were mostly ordinary login, profile, task, and ranking endpoints. Some extracted “URLs” were clearly bundled documentation or unrelated web content, which is why I’m not copying the entire string list into the post. A six-megabyte asset catalog is not evidence; it’s just a six-megabyte asset catalog.

The authority fields are still the best lead, but they point toward protocol understanding rather than a one-line cheat. I want to map the request and response classes, identify the message transport, and compare the values used by the normal UI with the values accepted by the local client. If the server is doing its job, malformed or elevated values should come back as a permission error.

For now, the useful result is narrower than “god mode found.” I have a searchable model of the client, a list of administrative-looking surfaces, and one concrete permission-management path worth tracing. That’s enough to keep digging without pretending that a class name is an exploit.
