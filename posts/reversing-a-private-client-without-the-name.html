Reverse Engineering a Distributed Client

15.09.26 / first notes

I’m deliberately leaving the name out of this one. The application is a privately installed Windows multiplayer client, and the point of these notes is the method, not handing the internet a neat set of search terms for somebody else’s software.

The first useful thing was simply identifying what kind of Unity build I was looking at. The main executable was accompanied by a large native assembly, a metadata file, and an il2cpp_data directory. That combination is the tell: this is an IL2CPP build, so the managed code isn’t sitting around as ordinary readable assemblies waiting for ILSpy.

There were still managed-looking DLL names in the scripting assembly manifest. That was a nice little trap. They’re useful clues about namespaces and features, but they aren’t the original source. The interesting logic lives in the native binary, with type and method metadata split across the binary and the metadata file.

Metadata first, guessing later

I used an IL2CPP metadata dumper against the native assembly and the global metadata file. The generated dummy assemblies and dump.cs were enough to turn a 100-plus-megabyte wall of machine code into something searchable.

Il2CppDumper.exe \
  "path\to\GameAssembly.dll" \
  "path\to\global-metadata.dat"

The output is not a magic decompilation. A generated method such as SetEntityPermissionsRequest tells us that a type and its signature existed. It does not tell us that the client will accept arbitrary values, or that the server will honor them. That distinction matters, especially in multiplayer software where the server is supposed to make the final decision.

I renamed the application-specific identifiers in these notes. For example, one scoped-permission request becomes SetEntityPermissionsRequest here. Same meaning, less fingerprinting.

The first real lead was permissions, not a cheat switch

The generated protocol definitions contained a cluster of fields that looked much more interesting than the usual UI and analytics debris:

EntityPermissions
ResourcePermissions
EventPermissions
SuspendPermissions
TaskPermissions
AutomaticSuspendPermissions
PermissionDetails

There were also request/response pairs for changing scoped permissions, manager-level permission updates, and a broadcast-style message carrying permission state. That gives us a real flow to follow: a panel creates a request, a transport sends it, and a response or broadcast updates the UI.

Several error values explicitly represented “no permission” or a permission failure. That’s useful because it tells us the authorization boundary is expected to be enforced somewhere. It also means a local toggle may only change what the client displays while the server continues to reject the operation. A button appearing is not the same thing as authority.

Debug panels are worth checking, carefully

String extraction found names resembling a server-switching panel, a test-data selection panel, a protobuf test panel, a performance debug menu, an administration popup, and a few export tools. I’m treating these as leads, not vulnerabilities. Debug code often ships accidentally, but it can also be dead UI, development-only scaffolding, or a panel protected by a server-side role check.

The next searches are deliberately boring:

rg -n -i -C 8 \
  'SetEntityPermissionsRequest|PermissionDetails|AdminAuthorityPanel|DebugServerPanel' \
  dump.cs

rg -n -i -C 8 \
  'EntityPermissions *=|PermissionDetails *=|CanManage|IsAdmin|IsGM' \
  dump.cs

I’m looking for the enclosing class and the code that decides visibility, not just names that contain “admin.” The useful questions are: what opens the panel, what fields are populated, where is the request sent, and does the client make a local decision based on a role or permission bit?

Hypothesis: a generic role-setting request

The first string-level pass suggested that the panel might send a generic account-role request containing a scope identifier, user identifier, role, and permission details. Nearby protocol classes had exactly those sorts of fields. That was a reasonable lead, but it was still inference by proximity. Nothing yet connected those classes to this button.

H0: confirmation button
      -> generic role request
      -> user + role + permission details

The native trace below falsifies that model for this panel. The actual request has only two protobuf fields: a scope-like identifier and an authority integer. Keeping the failed hypothesis in the notes matters because it shows which conclusion came from strings and which one came from control-flow evidence.

Correction: the first virtual call was just cleanup

This was a useful wrong turn. The address was real, but its managed identity was wrong in my working notes. The generated metadata maps 0x18317F2B0 to the panel’s close handler, not the confirmation handler. Once that mapping was corrected, the decompiled behavior made much more sense.

The tail call resolves through an IL2CPP virtual table:

MOV  R9, [object]        ; class/vtable pointer
XOR  R8D, R8D           ; immediate = false
MOV  DL, 1              ; destroy now = true
MOV  RAX, [R9 + 0x178]  ; virtual method pointer
MOV  R9,  [R9 + 0x180]  ; MethodInfo*
JMP  RAX

In this metadata layout, the vtable begins at 0x138, and each virtual entry occupies 0x10 bytes: an 8-byte function pointer followed by an 8-byte method-information pointer. Therefore:

(0x178 - 0x138) / 0x10 = 4

That makes +0x178 virtual slot 4 and +0x180 its paired MethodInfo*. Following the inheritance chain in the generated metadata led to the slot-4 override:

ScopedManagementPanel
  -> PrefabObject
    -> BaseBehaviour
      -> DisposableBehaviour

BaseBehaviour.Dispose(bool destroyNow = true, bool immediate = false)

The resolved target was renamed BaseBehaviour_Dispose in Ghidra. The call is therefore equivalent to:

this.Dispose(true, false);

The values 1 and 0 are disposal controls, not permission bits. The real confirmation path remains the method at 0x18317F310, with its generated callback at 0x18317F680. This is exactly why the metadata mapping has to be checked before interpreting constants in a native function. A plausible-looking integer is not evidence by itself.

The request is smaller than expected

The generated callback settled the packet schema. This is not the generic account-role request from the initial hypothesis. The concrete protobuf message has two application fields:

message SetScopeAuthorityRequest {
    optional int32 ScopeId   = 1;
    optional int32 Authority = 2;
}

The recovered object layouts line up with those field numbers:

Panel object
Offset   Alias              Use
------------------------------------------------------------
+0x78    _contextInfo       initialized with panel context
+0x80    _localScopeId      loaded during initialization
+0x84    _remoteScopeId     copied to request.ScopeId
+0x88    _currentChoice     copied to request.Authority
+0xA8    _permissionA       represents authority value 1
+0xB0    _permissionB       represents authority value 2
+0xB8    _confirmButton     binds confirmation handler

Request object
Offset   Alias              Protobuf field
------------------------------------------------------------
+0x18    _hasBits0          presence bitmap
+0x1C    scopeId_           field 1
+0x20    authority_         field 2

The first toggle callback at 0x18317F510 writes 1 to panel + 0x88. The second callback at 0x18317F580 writes 2. Initialization sets the toggles from the existing authority value without firing their listeners. The confirmation handler itself does not read either toggle; it sends whatever integer is already stored in _currentChoice.

toggle A callback  -> panel._currentChoice = 1
toggle B callback  -> panel._currentChoice = 2
generated callback -> packet.Authority = panel._currentChoice

The setter constants 1 and 2 seen inside the protobuf methods are a separate thing: they are presence-bit masks for fields 1 and 2. The actual authority value comes from panel + 0x88. Same numbers, different jobs. A small coincidence with excellent potential for wasting an afternoon.

There’s one especially useful distinction here. The side services speak HTTPS, so the capture mostly gives us DNS, TLS handshakes, timing, and connection sizes. The regional entry gateway uses a long-lived TCP connection whose application identifiers are visible in the payload. That stream is where the interesting correlation lives.

The capture ran for a little under three minutes from a Windows host. The local address, public service addresses, account identifiers, and the login token-like field are deliberately not copied here. The following is the technical map with those values generalized:

What actually sits inside the TCP stream

The core stream is not a raw protobuf byte stream. It has a small application envelope around each logical message:

TCP
  custom envelope
    length / envelope fields
    ASCII message identifier
    protobuf body

A captured frame had this general shape. The values are shown schematically so the example doesn’t become a fingerprint:

00 ?? 00 ?? | pb.LoginREQ | 00 00 00 00 | protobuf fields ...

The exact meaning of the envelope length fields is still open. The useful part is already established: the message name is visible, the body follows it, and one TCP segment can contain several logical messages. In other words, TCP segmentation and application framing are two different problems. Mixing them up is how packet parsers become haunted.

flowchart TD
    Bytes["TCP payload bytes"]
    Frame["Custom application envelope"]
    Name["Visible message identifier<br/>pb.SomeRequest"]
    Body["Google.Protobuf body"]
    Dispatch["Protocol dispatch"]
    Handler["Request or response handler"]

    Bytes --> Frame --> Name
    Frame --> Body
    Name --> Dispatch
    Body --> Dispatch --> Handler

The missing packet is itself a result

I searched the complete capture, all port-4000 payloads, and the reconstructed core conversation for the authority request and response names. Neither appeared.

pb.SetScopeAuthorityRequest   not observed
pb.SetScopeAuthorityResponse  not observed

That narrows the next experiment. The capture probably ended before the final confirmation, or the panel was opened without pressing Confirm. Another possibility is that the visible actions were upgrade and league-navigation controls rather than the permission toggles. The static path is still interesting; the dynamic proof just hasn’t reached its final packet yet.

The expected request, based on the decompiled callback, has only two application fields:

field 1: ScopeId    <- panel._remoteScopeId
field 2: Authority  <- panel._currentChoice

For the two known toggle paths, field 2 should be a protobuf varint with value 1 or 2. That’s a prediction from code, not a claim about what the server accepts.

Wireshark filters for the next pass

For a fresh capture, I don’t need to record every browser tab and Windows service again. These filters separate the useful stream from the wallpaper:

# Core protocol
tcp.port == 4000

# Visible application messages
tcp.port == 4000 && tcp contains "pb."

# The authority request we expect after one controlled confirmation
tcp.port == 4000 && tcp contains "SetScopeAuthorityRequest"

# Service discovery for the anonymized entry service
dns.qry.name contains "entry"

# Keep this unrelated flow out of the first pass
udp.port == 1337

If the message name is split across TCP segments, the byte filter may miss it. In that case, select a packet from the core stream, use Follow -> TCP Stream, and search the reconstructed ASCII stream. Once the right conversation is selected, recording its tcp.stream number makes later filtering much less annoying.

Reproduction record

I reproduced the trace by mapping the two VAs back to generated metadata, opening each function in Ghidra, recording incoming references, and exporting the decompilation plus direct and indirect call instructions. Every direct native target was then matched back to its generated VA entry. Finally, I followed the generic protocol method through packet allocation, callback invocation, the non-generic message path, network packing, protobuf serialization, and TCP transmission.

metadata identity
  -> native decompilation
  -> delegate binding
  -> object offsets
  -> protobuf setters
  -> generic protocol send
  -> network packer
  -> protobuf serializer
  -> TCP send

This proves what the client constructs and where it sends it. It does not yet prove what authority values 1 and 2 mean in business terms, whether other integers are accepted, or where the server enforces authorization. Those belong to the packet-capture and response-analysis phase.

What the strings did not show

No plaintext administrator password, session token, or obvious god-mode boolean appeared in the collected strings. The apparent URLs were mostly ordinary account and application endpoints. Some extracted “URLs” were clearly bundled documentation or unrelated web content, which is why I’m not copying the entire string list into the post. A six-megabyte asset catalog is not evidence; it’s just a six-megabyte asset catalog.

The authority request is mapped from UI state to the transport boundary, and the surrounding infrastructure is now visible enough to capture it without drowning in browser traffic. The missing piece is a short, controlled trace containing one toggle change and one Confirm click. If the server is doing its job, unsupported or unauthorized state changes should be rejected there.

For now, the useful result is narrower than “god mode found.” I have a reproducible map from two UI choices to a two-field protobuf request and the exact function that hands its serialized bytes to TCP. That is finally concrete enough to take to Wireshark.
