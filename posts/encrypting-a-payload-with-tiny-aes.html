// transmission 001

Hide encryption signatures from analysis

29.08.26 / 10 min read

I wanted to encrypt a byte buffer from C without wrapping another library or handing the whole job to a Windows API. The result is deliberately small: tiny-AES, CBC mode, a 256-bit key, and two short functions for PKCS#7 padding.

The test program does one round trip. It copies a harmless string into a fixed buffer, pads it to a multiple of 16 bytes, encrypts it in place, decrypts it, validates the padding, and prints the original text. Nothing is hidden behind a helper class. I can follow the bytes from the first memcpy to the last printf.

What is actually configured

The name AES-256 describes the key, not the block. AES always operates on 128-bit blocks. That means 16 bytes per block whether the key is 128, 192, or 256 bits. In my copy of aes.h, the relevant definitions are:

// #define AES128 1
// #define AES192 1
#define AES256 1

#define AES_BLOCKLEN 16 // AES always has a 128-bit block

#if defined(AES256) && (AES256 == 1)
    #define AES_KEYLEN 32
    #define AES_keyExpSize 240
#endif

AES_KEYLEN is 32 bytes, while AES_BLOCKLEN stays at 16. AES-256 also uses 14 rounds. The 240-byte expanded-key buffer holds fifteen 16-byte round keys: one before the first full round, thirteen for the middle rounds, and one for the last round.

Padding the input

CBC only accepts complete blocks. A 27-byte input cannot go straight into this function; its length has to become 32 bytes first. I used PKCS#7, where every padding byte contains the number of bytes added.

If five bytes are needed, the tail is 05 05 05 05 05. If the input is already aligned to 16 bytes, PKCS#7 adds a complete block of sixteen 10 bytes. That extra block is not wasted. It is what makes unpadding unambiguous.

static size_t pkcs7_pad(uint8_t* buffer, size_t len, size_t capacity)
{
    size_t padding = AES_BLOCKLEN - (len % AES_BLOCKLEN);

    if (len + padding > capacity) {
        return 0;
    }

    for (size_t i = 0; i < padding; i++) {
        buffer[len + i] = (uint8_t)padding;
    }

    return len + padding;
}

The reverse path checks more than the last byte. Every byte in the claimed padding range has to carry the same value. That catches malformed padding before the program treats the result as plaintext.

static size_t pkcs7_unpad(uint8_t* buffer, size_t len)
{
    if (len == 0 || len % AES_BLOCKLEN != 0) {
        return 0;
    }

    uint8_t padding = buffer[len - 1];

    if (padding == 0 || padding > AES_BLOCKLEN) {
        return 0;
    }

    for (size_t i = 0; i < padding; i++) {
        if (buffer[len - 1 - i] != padding) {
            return 0;
        }
    }

    return len - padding;
}

Padding validation is not authentication. CBC ciphertext can be modified, and observable padding failures can become a padding oracle. For anything exposed to untrusted input, the ciphertext needs authentication too.

How CBC chains the blocks

AES turns one 16-byte block into another 16-byte block. CBC supplies the chaining around it. Before the first plaintext block enters AES, it is XORed with the IV. Every block after that is XORed with the ciphertext immediately before it.

C[0] = AES(key, P[0] XOR IV)
C[i] = AES(key, P[i] XOR C[i - 1])

This is visible almost line for line in aes.c:

static void XorWithIv(uint8_t* buf, const uint8_t* Iv)
{
    uint8_t i;
    for (i = 0; i < AES_BLOCKLEN; ++i) {
        buf[i] ^= Iv[i];
    }
}

void AES_CBC_encrypt_buffer(struct AES_ctx* ctx,
                            uint8_t* buf,
                            size_t length)
{
    size_t i;
    uint8_t* Iv = ctx->Iv;

    for (i = 0; i < length; i += AES_BLOCKLEN) {
        XorWithIv(buf, Iv);
        Cipher((state_t*)buf, ctx->RoundKey);
        Iv = buf;
        buf += AES_BLOCKLEN;
    }

    memcpy(ctx->Iv, Iv, AES_BLOCKLEN);
}

Iv = buf is the chain. After Cipher returns, that section of the buffer contains ciphertext, so it becomes the XOR input for the next block. The operation is in place; the plaintext is replaced as the loop advances.

Decryption goes in the opposite order. The current ciphertext block is saved, AES is reversed, the result is XORed with the previous ciphertext block (or the original IV for block zero), and the saved block becomes the next IV.

Inside one AES-256 block

Internally, the 16 bytes are treated as a 4×4 byte state. Before the numbered rounds start, AES XORs that state with round key zero. Rounds 1 through 13 perform four operations. Round 14 skips MixColumns.

static void Cipher(state_t* state, const uint8_t* RoundKey)
{
    uint8_t round = 0;

    AddRoundKey(0, state, RoundKey);

    for (round = 1; ; ++round) {
        SubBytes(state);
        ShiftRows(state);

        if (round == Nr) {
            break;
        }

        MixColumns(state);
        AddRoundKey(round, state, RoundKey);
    }

    AddRoundKey(Nr, state, RoundKey);
}

01 / SubBytes

Each byte is replaced through the AES S-box. This is the nonlinear part of the cipher. Without it, the rest would reduce to linear operations that could be unwound with ordinary algebra. tiny-AES keeps the 256-byte S-box as a constant lookup table.

02 / ShiftRows

The first row stays put. The next three rows rotate left by one, two, and three positions. No byte value changes here; the bytes only move. The point is to stop each column from remaining an isolated group.

03 / MixColumns

Each column is multiplied by a fixed matrix in the finite field GF(28). In practical terms, a change to one input byte spreads across the four bytes in that column. tiny-AES does the field arithmetic with XOR and an xtime helper rather than normal integer multiplication.

04 / AddRoundKey

The state is XORed with the round key. Those keys are derived from the original 32-byte key by the AES-256 key schedule, which rotates words, applies the same S-box, mixes in round constants, and performs the additional AES-256 SubWord step halfway through each eight-word cycle.

The last round still runs SubBytes, ShiftRows, and AddRoundKey. It omits MixColumns. That detail is easy to miss when AES is reduced to a four-box diagram, but the break in the code makes it obvious.

The IV is part of the design

My current test uses a hard-coded IV:

uint8_t iv[AES_BLOCKLEN] = {
    0x10, 0x11, 0x12, 0x13,
    0x14, 0x15, 0x16, 0x17,
    0x18, 0x19, 0x1A, 0x1B,
    0x1C, 0x1D, 0x1E, 0x1F
};

That is useful for a repeatable test and wrong for real encryption. It even duplicates the second half of the demo key. For production, CBC needs a newly generated, unpredictable 16-byte IV for every encryption performed with a given key. The IV does not need to be secret. It can be stored directly before the ciphertext:

[ 16-byte IV ][ CBC ciphertext ... ]

It does need to come from a cryptographically secure random source. rand(), timestamps, counters, and hand-rolled generators are not substitutes. A small cipher dependency does not make random generation dependency-free; the program still needs a trusted source for keys and IVs.

There is another detail in the test that initially looks redundant:

AES_init_ctx_iv(&ctx, key, iv);
AES_CBC_encrypt_buffer(&ctx, buffer, padded_len);

AES_init_ctx_iv(&ctx, key, iv);
AES_CBC_decrypt_buffer(&ctx, buffer, padded_len);

The second initialization is required. The encryption function updates ctx.Iv to the last ciphertext block so that another call could continue the chain. Decryption has to restart from the original IV, not from that final block.

Why tiny-AES instead of BCrypt

Using tiny-AES means the cipher is compiled into the program. There is no bcrypt.dll import for this path, no provider setup, and no external crypto API to wrap. The source is small enough to step through, it works outside Windows, and unused modes can be disabled at compile time.

Import-based analysis tools sometimes treat crypto API calls as one signal among many. Removing that import changes the dependency and telemetry profile, but it does not make the operation invisible. AES lookup tables, key-schedule logic, high-entropy output, and the surrounding behavior are all observable. I see the benefit as control over a small dependency, not a way around analysis.

The trade is that more responsibility moves into my code. tiny-AES does not create keys or IVs, authenticate ciphertext, manage secrets, or provide the platform hardening and acceleration that a mature system crypto provider may offer. Its own documentation prioritizes size, simplicity, and portability over performance.

The round trip as it stands

The encryption path in main.c is short enough to read without abstraction:

uint8_t buffer[128] = { 0 };

const char* message =
    "Hello from tiny-AES. This message is longer than one block!";

size_t message_len = strlen(message);
memcpy(buffer, message, message_len);

size_t padded_len =
    pkcs7_pad(buffer, message_len, sizeof(buffer));

if (padded_len == 0) {
    printf("Padding failed.\n");
    return 1;
}

struct AES_ctx ctx;

AES_init_ctx_iv(&ctx, key, iv);
AES_CBC_encrypt_buffer(&ctx, buffer, padded_len);

For now, this is where the implementation is: AES-256-CBC, explicit PKCS#7 padding, a transparent in-place encryption path, and a verified decrypt/unpad round trip. Before treating it as more than a test, I would replace the fixed key and IV, add authentication (or choose an authenticated mode), make failures indistinguishable to an attacker, and clear sensitive key material when it is no longer needed.
