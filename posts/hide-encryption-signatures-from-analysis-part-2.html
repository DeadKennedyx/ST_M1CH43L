Hide encryption signatures from analysis - Part 2

30.08.26 / 11 min read

Part 1 removed the static forward and inverse S-box tables, generated Rcon during key expansion, and expanded the round schedule without a loop. That changed several easy file signatures, but the tableless S-box introduced a new set of readable algebraic clues: exponentiation by 254, a generic GF(28) multiplier, four byte rotations, and the affine constant 0x63. The field-doubling paths also loaded 0x1B directly.

Part 2 changes that representation again. I first construct the reduction term from runtime operands with a mixed Boolean-arithmetic identity. I then replace the complete algebraic S-box calculation with a fixed XOR/AND circuit and process the state in bit planes. The row permutation becomes lane wiring, column mixing shares its write-back with the round key, and decryption avoids the familiar inverse-matrix coefficients. The output remains AES-256-CBC; only the route through the executable changes.

The source for the experiment lives at github.com/DeadKennedyx/hidden-tiny-aes.

Focus on the deployed executable

The repository is not the artifact an analyst normally receives. C comments, macro names, and most private identifiers do not automatically become part of a normal MSVC Release PE. Without the PDB, a debugger still has machine code, constants, imports, strings, addresses, and runtime values, but not the original source-level explanation.

That distinction matters throughout this experiment. Removing a literal or a function name from C is not evidence by itself. The claim has to be checked against the final optimized executable produced by the deployment toolchain. It also needs a narrow definition: defeating one immediate-value search is different from preventing semantic recognition of AES.

Construct the reduction term at runtime

Part 1's finite-field doubling paths contained a direct reduction:

return (uint8_t)((x << 1) ^
    (((x >> 7) & 1) * 0x1B));

In the unoptimized ARM64 validation build, the compiler materialized that byte exactly as expected:

mov  w10, #0x1b
mul  w8, w8, w10
eor  w8, w8, w9, lsl #1

The replacement starts with the integer identity:

A + B = (A XOR B) + 2 * (A AND B)

The high bit of the byte being doubled becomes a runtime carry. When it is zero, both identity operands are zero. When it is one, the operands become 0x17 and 0x04:

0x17 XOR 0x04       = 0x13
2 * (0x17 AND 0x04) = 0x08
0x13 + 0x08          = 0x1B
static NOINLINE uint8_t add_identity(uint8_t a,
                                     uint8_t b)
{
    return (uint8_t)((a ^ b) + ((a & b) << 1));
}

static uint8_t reduction_term(uint8_t x)
{
    const uint8_t carry = (uint8_t)(x >> 7);
    const uint8_t a = (uint8_t)(carry * 0x17);
    const uint8_t b = (uint8_t)(carry << 2);

    return add_identity(a, b);
}

The no-inline boundary keeps the optimizer from seeing both correlated operands in the caller and simply rematerializing their sum. The final local -O0, -O2, and LTO disassemblies contain no mov ..., 0x1B. They do contain the runtime XOR, AND, and shifted addition.

This does not make the value unobservable. A debugger can stop after the addition and see 0x1B in a register. Static analysis can also propagate the carry and solve the identity. The defensible result is that the direct immediate signature is gone, not that the reduction polynomial is unknowable.

One circuit removes four S-box clues

Trying to wrap 254, 0x63, and every rotation in separate opaque expressions would create a large collection of transformations that a decompiler might simplify. A fixed Boolean circuit replaces the entire construction at once:

Current clue Better representation
Exponent 254 Fixed Boolean S-box circuit
Generic GF multiplication XOR/AND network
Rotations Explicit bit equations and wire permutations
Affine constant 0x63 Fold its bits into output inversions
Fourteen rounds Fuse round operations; the count cannot truly disappear

I adapted BearSSL's MIT-licensed translation of the Boyar-Peralta AES S-box circuit. Eight uint32_t values hold eight bit planes. For a state transformation, their low sixteen lanes represent the sixteen state bytes, so one fixed network calculates sixteen substitutions in parallel. Key expansion uses four lanes for each substituted word.

/* top linear section */
y14 = x3 ^ x5;
y13 = x0 ^ x6;
y9  = x0 ^ x3;

/* nonlinear section */
t2 = y12 & y15;
t3 = y3 & y6;
t4 = t3 ^ t2;

/* output section */
s6 = t56 ^ ~t62;
s7 = t48 ^ ~t60;
s1 = t64 ^ ~s3;
s2 = t55 ^ ~t67;

The complete circuit is straight-line XOR, AND, and NOT. There is no exponent variable, generic field multiplication loop, byte-rotation helper, S-box lookup, or explicit 0x63. The output complements incorporate the affine offset into individual bit equations.

Reuse the circuit for inverse substitution

Decryption needs the inverse S-box. Duplicating another large optimized circuit would increase the executable and introduce a second stable fingerprint. Instead, explicit linear input wiring transforms the byte, the same forward circuit runs once, and the inverse linear wiring transforms the result:

q0 = ~q[0];
q1 = ~q[1];
q2 =  q[2];
q3 =  q[3];
q4 =  q[4];
q5 = ~q[5];
q6 = ~q[6];
q7 =  q[7];

q[7] = q1 ^ q4 ^ q6;
q[6] = q0 ^ q3 ^ q5;
/* six more explicit output equations */

boolean_substitute(q);

/* apply the same inverse-affine wiring again */

The NOT operations carry the constant bits. The inverse path therefore has no inverse lookup table, no 0x05 affine shorthand, and no second field-inversion implementation.

Turn ShiftRows into wiring

Bit planes already require each input byte to be assigned to a lane. Instead of substituting all bytes and then moving them through a recognizable row-shift function, the loader places each source byte directly in its post-shift destination lane:

for (column = 0; column < 4; ++column) {
    for (row = 0; row < 4; ++row) {
        const unsigned lane = (column * 4) + row;
        const unsigned source_column =
            (column + row) & 3U;

        load_lane(q, state[source_column][row], lane);
    }
}

The reverse path changes the source equation to (column + 4 - row) & 3. There are no separate ShiftRows or InvShiftRows functions in the implementation. The permutation is a property of how values enter the circuit.

Remove the remaining generic multiplication

Deleting the algebraic S-box removes its general gf_mul(), but the original inverse column step still expressed multiplication with the familiar 09, 0B, 0D, and 0E coefficients. I replaced that matrix expression with a double-doubling pre-transform followed by the same XOR network used for forward column mixing:

u = xtime(xtime((uint8_t)(a ^ c)));
v = xtime(xtime((uint8_t)(b ^ d)));

a ^= u;
b ^= v;
c ^= u;
d ^= v;

all = (uint8_t)(a ^ b ^ c ^ d);
out0 = a ^ xtime((uint8_t)(a ^ b)) ^ all;
out1 = b ^ xtime((uint8_t)(b ^ c)) ^ all;
out2 = c ^ xtime((uint8_t)(c ^ d)) ^ all;
out3 = d ^ xtime((uint8_t)(d ^ a)) ^ all;

xtime remains because AES still needs field doubling for column mixing and Rcon generation. Its reduction term now comes from the runtime identity described earlier. What disappears is the general two-input multiplier and the four inverse coefficient immediates.

Fuse the visible round stages

Each full forward layer now has two combined phases. The bit-plane loader performs substitution and row movement together. Column diffusion and round-key XOR share the same write-back:

old:
SubBytes -> ShiftRows -> MixColumns -> AddRoundKey

new:
substitute_with_lane_wiring -> mix_and_key_writeback

Decryption follows the corresponding reverse data flow. Key bytes are XORed into the four column values before the inverse-mixing pre-transform, and the final four results are written once. The final encryption and decryption layers use the wired substitution followed directly by their key combination because AES omits column mixing there.

The top-level schedule is still expanded into thirteen full layers plus the final AES-256 layer. Fusing operations removes clean function boundaries; it does not change the fact that AES-256 has fourteen nonlinear layers. An analyst following runtime data flow can still count them, and the expanded key remains another strong clue.

Proving that encryption remained intact

The Boolean circuit is too large to trust from one successful message. I added a regression program that includes an independent algebraic reference implementation and checks every possible byte:

check                                      result
forward Boolean substitution, 256 inputs  pass
inverse(forward(x)), 256 inputs            pass
runtime field doubling, 256 inputs         pass
NIST AES-256 ECB known-answer vector       pass
NIST AES-256 CBC known-answer vector       pass
demo ciphertext versus previous build     identical
demo ciphertext versus OpenSSL             identical
ASan and UBSan                             clean

The checks pass under an unoptimized build, an optimized LTO build, and a sanitizer build. The fixed demo still produces:

825c4519c61fc280235b1237c3478563
e8f7c7005b3cc1a3e159a901a92a91d8
2a6801f0e5d290f1013ab8b687a92922

The optimized validation artifact contains no direct materialization of 0x1B, 0x63, or 254, and no symbols named for the old S-box, rotation, generic field multiplication, or individual round stages. This result is compiler-specific, so the same inspection must be repeated on the exact MSVC Release PE that is deployed.

What this still does not hide

A fixed circuit can itself become a signature. The Boyar-Peralta network is public and its data flow can be fingerprinted even when its temporary names are absent. Fourteen repeated nonlinear layers, the key-expansion dependencies, 16-byte state, CBC chaining, and known input/output behavior still support semantic identification.

Dynamic analysis is stronger still. A debugger can collect all 256 circuit inputs and outputs, observe the computed reduction byte, or stop after key expansion and dump the complete round-key schedule. This repository also deliberately embeds a demonstration key, IV, and a string containing tiny-AES. Those make sense for a reproducible experiment, not for protecting a production secret.

The outcome is narrower and measurable: several easy static anchors have been replaced by a Boolean data-flow problem, while every tested AES result remains unchanged. That raises the cost of analysis without treating representation changes as cryptographic security.
